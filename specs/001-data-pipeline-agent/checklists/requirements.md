**第 8 轮**(采纳 OpenMetadata bot 身份方案):

- **本轮的落法回答了用户"是否作为前置条件更合适"这一提问:三层,不是一层。** 前置条件清单(给部署的人)+ 功能需求(可测的系统行为)+ **启动自检**(证明边界真的生效)。只写成前置条件的风险是:没人验的前置条件等于愿望——本 spec 已有先例,"平台管理员须为仓库协作者"当初也是前置条件,最终落成 FR-020 运行时校验。
- **自检必须含负向探测(FR-074)。** 一个被误授写权限的只读 bot **不会有任何症状**,FR-011 会悄悄失效。因此只验"令牌可用"不算通过,只读 bot 的写探测**必须被 OpenMetadata 拒绝**。这与前几轮反复应用的原则一致:只会说"没问题"的检查没有价值。

- **新增 FR-078** 把"目录 Writer ≠ 平台管理"从凭证清单的说明升格为需求:运维发布 bot 不得具备域、角色、策略的管理能力。

**第 12 轮**(收件箱调研:闸门待办能否跨用户送达):

- **推翻了我自己第 11 轮的一个断言。** 我当时称"omnigent 没有面向人的通知能力",依据是 grep 不到 `sys_notify` 之类的**工具名**。**错了**——收件箱是 **UI 侧的聚合面**而非 agent 工具,所以工具名搜索必然漏掉。它把各会话快照的待处理审批请求跨会话汇总(`web/src/lib/inbox.ts`)。同时作废的还有"审批人通常不在那个会话里,点不到"这条论证。
- **跨用户送达链路已逐环核实**:`sys_session_share` 按邮箱授予具名用户访问权 → 会话列表以 `accessible_by=user_id` 过滤(注释明写 *shared sessions still surface for the "Shared with me" tab*)→ 收件箱基于该列表聚合待办 → 子 Agent 的请求被服务端镜像到父会话。因此**四道闸门涉及三个不同的人**这一难题在机制上成立。

**第 13 轮**(用户指出:本 spec 定义的是一个 omnigent Agent,一切能力必须由 Agent 定义机制承载):

- **这是开发前必须补的实质缺口。** 原 spec 通篇写"系统 MUST…",读起来像要造一套应用,会让 `/speckit-plan` 严重跑偏。新增《实现载体》章节明确:交付物是一个 **Agent 定义包**(`config.yaml` + `agents/*` + `tools/mcp/*` + `guardrails.policies` + `skills/*` + prompt),"系统"即指此包。
- **指出需求实际跨了三个层次,必须分开读**:① Agent 长什么样(声明式配置)② Agent 怎么工作(策略 + skills + prompt)③ **Agent 产出的管线长什么样**。第 ③ 层(快照不覆盖、门禁项、回滚、幂等)是 **Agent 的验收标准,不是 Agent 的构建规格**——把它当成"要在 Agent 定义里实现的功能"是最容易犯的规划错误。已落为 FR-092。
- **逐条认领了载体**,并区分强弱。核实到的两处关键事实:
