# Phase 1 · 数据模型

本特性**不引入任何新的持久化存储**。下列实体分三类:寄存于 omnigent 运行时既有结构的(会话标签)、存放于外部系统的(GitHub、OpenMetadata)、以及仅存在于一次调用中的传输结构(工具入参与返回值)。

---

## 一、寄存于会话标签的状态

闸门状态是本特性唯一的**运行时可变状态**,以会话级 guardrails 标签承载。标签是字符串键值对,由策略读写。

### 标签存放在**编排者的会话**上

omnigent 的标签是**逐会话**的:子 Agent 各有自己的会话,**不继承**父会话的标签
(`omnigent/runtime/policies/builder.py`——从 root 继承的只有运行时会话策略与两个成本 key)。

因此下述三族标签全部存放在**编排者**的会话上,并由此决定了职责划分:

| 角色 | 做什么 |
| --- | --- |
| 子 Agent | 用自己作用域内的凭证**读取并报告观测值**(找到的值、量到的数)。不做判定。 |
| 编排者 | 在自己会话里运行确定性比较工具(核验、门禁),据其**真实返回值**推进标签;并据标签决定派发什么。 |

**为什么不是子 Agent 自己判定**:判定结果会落在一个别人读不到的标签空间里,
闸门形同虚设。这一点在实现期由测试发现(见 cycle-log 的 U73–U77)。

**派发必须带阶段参数**:编排者对子 Agent 的每次派发都携带 `phase`
(`plan` / `governance` / `build` / `release` / `switch`)。闸门按**这个参数**判定,
而不是按任务描述的措辞——措辞由模型自己写,参数不是。

### `pipely.flow`

一次流程实例的身份与类型。会话创建时写入,此后不变。

| 键 | 值 | 说明 |
| --- | --- | --- |
| `pipely.flow.pipeline` | 管线标识 | 会话唯一的输入之一;上下文靠它去事实来源取 |
| `pipely.flow.kind` | `delivery` \| `operation` | 交付迭代 / 日常运行。决定适用哪几道闸门 |

**约束**:一个会话只承载一次流程实例(FR-099)。策略在检测到已存在不同 `pipeline` 值时必须拒绝,而非覆盖。

### `pipely.gate`

当前已通过的闸门。**只进不退**,由策略在对应条件满足时推进。

| 值 | 含义 | 推进条件 | 适用流程类型 |
| --- | --- | --- | --- |
| *(未设置)* | 流程未开始 | — | 两者 |
| `g1_passed` | Spec 已冻结 | 开发负责人确认 | `delivery` |
| `g2_passed` | 治理已落地 | **只读核验工具返回全部断言通过** | `delivery` |
| `g3_passed` | 发布就绪 | 变更请求已合并、制品引用已产出 | `delivery` |
| `g4_passed` | 已上线 | 运维负责人批准切换 | 两者 |

**状态迁移**:`g1 → g2 → g3 → g4`(delivery);`(空) → g4`(operation,日常运行只需门禁与上线批准)。

**关键约束**:`g2_passed` **只能由工具的真实返回值触发**(策略在 `tool_result` 上求值),不得由模型自述触发(FR-097)。

**质量门禁不是闸门**。它跑在阶段 4,夹在 `g3_passed` 与 `g4_passed` 之间,不推进 `pipely.gate`;它的结论记在下面的 `pipely.quality`。把它接成闸门会替换掉"人合并变更请求"这道人工检查点。

### `pipely.quality`

阶段 4 质量门禁的结论。**不是闸门**,是切换审批的前置条件。

| 值 | 含义 | 写入条件 |
| --- | --- | --- |
| *(未设置)* | 本版本尚未跑过门禁 | — |
| `passed` | 五项门禁全部达标 | **门禁工具返回 `passed=true`** |
| `failed` | 任一项未达标,或五项未齐 | 门禁工具返回 `passed=false` |

**为什么单列一族**:切换线上指向需要**同时**满足 `pipely.gate ≥ g3_passed`(发布就绪)与 `pipely.quality = passed`(本次运行的数据合格)。两者含义不同——前者说"这个版本可以上",后者说"这一跑的结果可以用"。同一条管线重跑一次,前者不变,后者要重新判定。

**关键约束**:与 `g2_passed` 同理,`pipely.quality` **只能由门禁工具的真实返回值写入**(FR-097)。模型自述"门禁通过"不写入,因而也无法据此请求切换。

### `pipely.preflight`

前置条件校验结果。首个工具调用时由策略写入;未通过则后续一切操作被拒。

| 键 | 值 | 说明 |
| --- | --- | --- |
| `pipely.preflight.status` | `passed` \| `failed` | 未设置视同未校验,拦截 |
| `pipely.preflight.missing` | 逗号分隔的缺失项 | 供报错时逐项列出(FR-060) |

## 二、存放于 GitHub 的结构

### 统一 Spec

一条数据管线的唯一事实来源,以文件形式存放于该管线的代码仓库。

**必备条目**(FR-007,九类,缺一不可):数据契约、字段定义、质量阈值、验收用例、分层设计、治理资产模型、角色分工、版本与回滚策略、权限申请清单。

**状态**:草案 → 已评审 → 已冻结 → 已变更。冻结发生在 G1。

### 治理变更请求包

交给平台管理员亲手执行的一次治理变更,以 Pull Request 形式提交。**变更请求本身即审批载体**——合并即批准。

| 产物 | 内容 | 用途 |
| --- | --- | --- |
| 操作手册 | 逐步操作,每步含操作、参数、预期结果、核验方式、回滚步骤(FR-013) | 人照着执行 |
| 状态断言 | 执行后应达到的、**机器可判定**的状态 | 核验工具的输入 |
| 只读核验脚本 | 逐条比对断言 | 由核验工具调用 |

**状态**:待审 → 已批准 → 已执行 → 已核验 / 核验失败。

**内容约束**:手册必须基于目录的**实时状态**生成,并标出与既有资产的命名或归属冲突(FR-014)——照 Spec 生成一份注定失败的手册是不可接受的。

## 三、存放于 OpenMetadata 的结构

### 制品引用

G3 到 G4 的**唯一交接物**。不可变,不含任何可写源码位置(FR-023)。

| 字段 | 说明 |
| --- | --- |
| 代码标签 | 该次发布的仓库标签 |
| 制品标签 | 构建产物标签 |
| **冻结的质量阈值** | 该版本的门禁判定依据 |
| **冻结的验收断言** | 该版本的验收依据 |

**为什么要冻结阈值与断言**:运维发布 Agent **无 shell、读不了仓库**,若不随制品引用冻结,它拿不到门禁判定所需的契约(FR-101)。

**不可编辑**:需要变更就走新版本;代码仓库始终是意图的唯一可编辑来源(FR-102)。

### 版本标识族

五类互相独立,**不得用同一个标识兼表两类**(FR-040):

| 类别 | 产生时机 | 产生方 |
| --- | --- | --- |
| 代码版本 | G3 合并后 | 管线开发负责人 |
| 制品版本 | G3 后构建 | 架构开发 Agent |
| 数据快照版本 | 阶段 4 每次运行 | 运维发布 Agent |
| 查询副本版本 | 阶段 4 | 运维发布 Agent |
| 线上指向 | G4 切换 | 运维发布 Agent(获批后) |

**"哪个版本在线"既不是分支状态也不是标签状态,而是线上指向的状态。** 回滚只动这一项。

### bot 身份

Agent 访问 OpenMetadata 的服务身份,与人类身份完全分离。

| bot | 权限 | 粒度 | 创建批次 |
| --- | --- | --- | --- |
| 治理审计 | 目录只读 | 全局共用 | **第 0 批,手工** |
| 架构开发 | 正式只读;**开发沙箱 Domain 内可写** | 全局共用 | 第 1 批,走 G2 |
| 服务验证 | 只读消费 | 全局共用 | 第 1 批,走 G2 |
| 运维发布 | 目录 Writer(**不含**域/角色/策略)+ Airflow 操作 | **每条管线一个** | 第 1 批,走 G2 |

**引导顺序**:治理审计 bot 必须先由人手工建好,否则它读不了目录、生成不了变更请求包——而其余 bot 正是该包要建的东西(FR-076)。

## 四、传输结构(仅存在于一次调用)

### 核验报告

只读核验工具的返回值。**策略据此写 `pipely.gate` 标签,因此其结构是硬契约**。

| 字段 | 说明 |
| --- | --- |
| 总体判定 | 全部断言是否通过 |
| 逐条结果 | 断言、期望值、**实际值**、判定 |
| 缺失步骤 | 未通过时,需要补做的具体步骤(FR-018) |

**幂等**:重复核验结果一致且不产生任何副作用(FR-019)。

### 质量报告

质量门禁工具的返回值。门禁项至少包括记录数、异常率、结构一致性、黄金用例结果、查询性能;**每项必须输出实际值与阈值的对比**(FR-027)——只给"通过/不通过"不可接受,因为"刚好通过"会被误当作无风险。

### 权限自检报告

bot 权限自检工具的返回值。**必须包含负向探测结果**(FR-074):只读 bot 的写操作探测**被拒绝**才算通过;仅验证"令牌可用"不算通过。

| 字段 | 说明 |
| --- | --- |
| 逐 bot 结果 | bot、应有权限、实际权限、判定 |
| 负向探测 | 探测动作、是否被拒、拒绝原因 |
| 越权项 | 权限宽于职责的具体项(FR-075) |

## 五、实体关系

```text
统一 Spec ──定义──> 治理资产模型 ──G2 落地──> OpenMetadata 资产
    │                                              │
    │                                          bot 身份(4 类)
    │                                              │
    └──G3 冻结阈值与断言──> 制品引用 ──G4──> 线上指向
                                │                  │
                          数据快照版本 ──> 查询副本版本
                                                   ↑
                                            回滚:指回上一副本

会话 ── 1:1 ──> 流程实例 ── 携带 ──> pipely.flow / pipely.gate / pipely.preflight 标签
```
