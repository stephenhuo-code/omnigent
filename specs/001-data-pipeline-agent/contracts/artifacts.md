# 契约 · 产物结构

本文件定义跨 Agent、跨系统传递的产物结构。它们是**契约**而非实现细节——结构变了,消费方就失灵。

---

## 制品引用

**G3 到 G4 的唯一交接物。** 架构开发 Agent 产出,运维发布 Agent 消费。

```
制品引用
├── 代码标签          该次发布的仓库标签
├── 制品标签          构建产物标签
├── 冻结的质量阈值    该版本门禁判定的依据
└── 冻结的验收断言    该版本验收的依据
```

**三条硬约束**:

1. **不含任何可写源码位置** —— 不得出现分支名、工作区路径或仓库检出路径(FR-023)。运维侧从**结构上**够不着源码,而不是靠约定不去碰。
2. **必须包含冻结的阈值与断言** —— 运维发布 Agent 无 shell、读不了仓库;若不随制品引用冻结,它拿不到门禁判定所需的契约(FR-101)。
3. **不可编辑** —— 要变更就走新版本。代码仓库始终是意图的唯一可编辑来源;冻结件只是该版本的不可变快照(FR-102)。

**为什么冻结不制造第二真相源**:它与数据快照同理——是某一版本的不可变副本,不是可编辑的平行副本。冻结发生在 G3 合并打标签的那一刻,之后该版本的契约就不该再变。

## 治理变更请求包

**Agent 产出,人执行。** 以 Pull Request 形式提交到 GitHub,**合并即批准**。

```
变更请求包
├── runbook          逐步操作手册
├── assertions       执行后应达到的状态断言(机器可判定)
└── verify           只读核验脚本
```

### runbook 的每一步

| 字段 | 说明 |
| --- | --- |
| 操作 | 要做什么 |
| 参数 | 具体取值 |
| 预期结果 | 做完应该看到什么 |
| **核验方式** | 怎么确认这一步成了 |
| **回滚步骤** | 做错了怎么退 |

后两项不可省(FR-013)——少了核验方式,人无法自查;少了回滚步骤,出错只能硬着头皮往前。

### assertions 的要求

**必须机器可判定** —— 它是 `verify_governance` 工具的输入,而该工具的返回值是 `g2_passed` 标签的唯一合法来源。写成"确认配置正确"这类人话,核验就无从执行。

### 生成时的约束

手册**必须基于目录的实时状态生成**,并标出与既有资产的命名或归属冲突(FR-014)。照着 Spec 生成一份注定失败的手册是不可接受的——那会让人白跑一趟才发现撞名。

### 状态流转

```
待审 ──合并──> 已批准 ──人执行──> 已执行 ──核验──> 已核验 (G2 通过)
                                              └──> 核验失败 (G2 不通过,给出需补做的步骤)
```

## 会话输入

一次流程实例启动时的**全部**输入。除此之外不携带任何上下文(FR-100)。

| 字段 | 说明 |
| --- | --- |
| 管线标识 | 用它去事实来源取上下文 |
| 流程类型 | `delivery`(交付迭代)或 `operation`(日常运行) |

**为什么只传标识**:上下文一律在会话开始时从事实来源重新取——**git 存意图**(Spec、数据契约、阈值、断言、作业定义),**OpenMetadata 存现状**(当前版本、上次运行结果、线上指向、资产状态)。会话间传递上下文必然导致跨天、跨会话拿到陈旧数据。

## 报告类产物

三份报告的结构见 [tools.md](./tools.md),此处只记它们的**消费关系**:

| 报告 | 产出方 | 消费方 | 后果 |
| --- | --- | --- | --- |
| 核验报告 | `verify_governance` | `gates.record_gate_passage` 策略 | 决定 `pipely.gate` 能否推进到 `g2_passed` |
| 质量报告 | `quality_gate` | 运维负责人(G4 审批的判断依据) | 决定是否批准切换线上指向 |
| 权限自检报告 | `bot_selfcheck` | `preflight.run_preflight` 策略 | 决定 `pipely.preflight.status` |

**共同约束**:三份报告都必须给出**实际值**,而不只是判定。理由一致——"通过"不带实际值,就无法判断是"稳过"还是"擦线过",也无法在失败时定位。
