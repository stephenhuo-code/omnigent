数据管线生命周期 Agent

以五个阶段说明三个人类角色与四个子 Agent 的职责、权限及 OpenMetadata 交互，并以约 1451 万条书目数据的搜索管线作为开发与验收示例。

本文档与 specs/001-data-pipeline-agent/spec.md 保持一致；规范以 spec 为准，本文档提供流程视图与书目管线实例。

14,517,522有效书目记录
59Curated Parquet 文件
36受控学科标签
5Corpus MCP 只读工具

角色模型：三个人类角色 + 四个子 Agent

凭证边界即职责边界。没有任何 Agent 持有平台管理凭证——需要该权限的操作一律由平台管理员亲手执行。

人 · 平台管理员

治理授权与亲手执行

评审并合并治理变更请求，亲手在 OpenMetadata 中创建 Domain、Data Product、Service、角色与策略。把守 G2。管理员凭证不进入 omnigent。

人 · 开发负责人

需求确认与代码合并

确认 Spec、评审并合并代码变更请求、批准开发过程中的推送。把守 G1 与 G3。

人 · 运维负责人

上线批准与回滚决策

批准线上指向切换、决定回滚、处理运行告警。把守 G4。

Agent · 架构开发

阶段 1、3

Spec 规划、代码与测试、调度作业定义、开变更请求。凭证：代码仓库写、测试环境、OpenMetadata 只读 bot（查数据源、中间表与落地表的结构与归属）。唯一具备 shell 的子 Agent，写入限于其工作区。

Agent · 治理审计

阶段 1、2

可行性评审、生成治理变更请求包、人执行后只读核验、漂移检测。凭证：OpenMetadata 只读 bot。无 shell，不执行任何治理写操作。

Agent · 运维发布

阶段 4

触发 Airflow 作业、判定质量门禁、上线切换、回滚、同步运行状态。凭证：Airflow 操作、索引构建、线上指向、OpenMetadata Writer bot。无 shell，够不着源码。

Agent · 服务验证

阶段 5

以最终用户视角只读消费管线服务，同时充当权限边界的活体检验。凭证：只读 bot。无 shell。

两条关键分界：其一，治理审计 Agent 不执行任何治理写操作——阶段 2 的操作简单但权限极高、每条管线只做一次，自动化收益小、风险大，故改为出手册、人执行、Agent 只读核验。其二，调度作业的“定义”与“运行”分属两个 Agent——定义是代码，走变更请求；运行是操作，由运维发布 Agent 触发。

五阶段主责总览

阶段 1 · 架构开发 + 治理审计

管线设计

  • 明确数据源、字段、质量规则和搜索需求。
  • 设计 Raw → Curated → Index → MCP。
  • 定义 OM 资产模型、角色分工、验收标准和版本策略。
  • 输出 Spec、数据契约和实施计划。
  • 治理审计 Agent 只读读取目录现状，评审平台可行性与权限边界。
  • 通过 G1 Spec 冻结后方可进入下一阶段。
阶段 2 · 平台管理员亲手执行

治理空间初始化

  • 治理审计 Agent 产出变更请求包：操作手册 + 状态断言 + 只读核验脚本。
  • 包提交到 GitHub，合并即批准；异步进行，不阻塞任何会话。
  • 平台管理员亲手在 OM 与检索平台执行手册。
  • 治理审计 Agent 只读核验实际状态，核验通过才过 G2。
  • 带写权限的 bot 也在此批创建与授权。
阶段 3 · 架构开发

管线开发与验收

  • 按 Spec 开发数据处理、服务、OM 同步与调度作业定义。
  • 以只读身份访问 OM，查数据源定义、中间表与落地表的结构与归属。
  • 在独立工作区与任务分支中工作，写入受限于该工作区。
  • 为 Spec 中每条验收用例产出自动化测试并跑通。
  • 开 Pull Request；Agent 不合并，由开发负责人合并并打标签。
  • 过 G3 后交接不可变制品引用，运维侧拿不到源码位置。
阶段 4 · 运维发布

上线与日常运维

  • 按制品引用部署作业定义到 OM 自带的 Airflow，按计划或事件触发。
  • 数据变化后创建新快照与新版本索引，禁止覆盖旧版本。
  • 质量门禁全绿后，切换 books-current 作为一次独立审批送达运维负责人（G4）。
  • 向 OM 同步版本、计数、质量和运行状态。
  • 失败时保持旧版本或回滚；仅平台对象/策略变更才升级平台管理员。
阶段 5 · 服务验证

配置与使用

  • 服务验证 Agent 以只读 bot 启动，不持有任何写凭证。
  • 先用 OM MCP 理解语义，再用 Corpus MCP 搜索书籍。
  • 每条结果带命中原因，不暴露内部路径类字段，分页受限。
  • 任何写入、索引创建、指向切换尝试都必须失败。
  • 本阶段只读，不设闸门——它是 G4 之后的验证动作。

四道人工闸门

阶段是职责划分，闸门是流程卡点，两者不必一一对应。闸门确认与单个危险操作的审批是两种机制，一方通过不隐含另一方通过。

G1 · Spec 冻结

阶段 1 → 2

Spec 条目齐备、可行性评审结论为“可实施”、权限申请清单已确认。
把守人：开发负责人
通道：对话轮次

G2 · 治理落地

阶段 2

变更请求包已合并、平台管理员已亲手执行、只读核验通过。
把守人：平台管理员
通道：变更请求包（异步）

G3 · 发布就绪

阶段 3 → 4

测试全绿、代码变更请求已合并并打标签、制品引用已产出。
把守人：开发负责人
通道：对话轮次 + 合并

G4 · 上线

阶段 4 内

新版本已构建、质量门禁全绿，仅剩切换线上指向。
把守人：运维负责人
通道：交互式审批

四条交互通道,职责不重叠

任务回执
子 Agent 完成 → 唤醒编排者。机器对机器，完成即自动唤醒，禁止轮询。
交互式审批
“我可以做吗”——Agent 亲自执行危险操作前请求许可。经收件箱送达，阻塞该次操作，秒~天。
变更请求包
“请你来做”——需要人亲自执行的高权限操作。载体在 GitHub，待办经收件箱送达。
对话轮次
阶段闸门的推进确认。编排者结束回合等待人回应。
许可与委派是两回事：交互式审批批准后 Agent 继续执行；变更请求包批准后 由人执行，Agent 事后只做核验。

审批通道的落地形态:收件箱

待处理的审批请求会跨会话聚合到运行时的收件箱页面，人不需要待在某个会话里。这解决了本设计最棘手的一个问题：四道闸门涉及三个不同的人，而会话通常只由其中一人发起。

①
会话被共享给目标用户（按邮箱授予具名用户，可设读/编辑/管理三级）。
②
会话列表按“该用户是否有权限记录”过滤，因此共享给我的会话会出现在我的列表中。
③
收件箱基于该列表拉取各会话的待处理审批请求并聚合。
④
子 Agent 发起的请求会被服务端镜像到父会话，因此同样可达。
三条必须落实的约束：其一，审批权是单独委派的，Agent 授不了——共享工具只能授访问级别，审批权默认关闭，必须由会话所有者单独委派。这是刻意的：Agent 不能自己给自己指定批准人。其二，Agent 的共享能力默认关闭，需显式开启“仅具名用户”一档，不得开匿名公开档。其三，权限是会话级而非单条审批级——为让管理员看到一条治理审批，必须把整个会话共享给他。

最后一条是已知的权限放大，本设计选择接受：三个人类角色本就是同一条管线的协作者，互相可见有利于透明与审计。

阶段 1：管线设计——架构开发 Agent 主责

1

需求与数据契约

架构开发 Agent
明确数据源、字段、质量规则、搜索场景、数据规模和更新频率；缺少影响设计的关键信息时提问而非静默取默认值。
输出
数据契约、字段定义、质量阈值和验收用例。
2

技术与治理设计

架构开发 Agent
设计分层链路，定义 OM 资产模型、角色分工、版本与回滚策略。
治理审计 Agent
以只读方式读取目录现状，评审平台可行性与权限边界，给出“可实施 / 需修改”的明确结论。
输出
统一 Spec、实施计划和权限申请清单。
职责边界：架构开发 Agent 提出业务定义；治理审计 Agent 基于目录实时状态评审。通过 G1 前不生成变更请求包，更不创建任何治理资产。

阶段 2：治理落地——Agent 出手册，平台管理员亲手执行

这些操作简单但权限极高，且每条管线只做一次——自动化收益小、风险大。因此 Agent 不执行，只出手册与核验。

1

生成变更请求包

治理审计 Agent
读取目录实时状态（现有资产、命名冲突、当前策略），产出三件产物：逐步操作手册、执行后状态断言、只读核验脚本。手册每一步含操作、参数、预期结果、核验方式与回滚步骤。
提交
以 Pull Request 形式提交到 GitHub——变更请求本身就是审批载体。
2

审批与执行

平台管理员
评审并合并 PR（合并即批准），随后亲手在 OpenMetadata 与检索平台按手册执行。
不阻塞
审批与执行都在会话之外完成，编排者结束回合；系统不轮询审批状态，由人回到会话重新驱动。
3

只读核验

治理审计 Agent
以只读方式逐条比对断言，失败项指明期望值与实际值。核验幂等，重复执行结果一致且无副作用。
G2 闸门
任一断言不满足则不通过，并给出需要补做的具体步骤。

bot 身份分两批创建,按风险切分

这里有个引导顺序问题：治理审计 Agent 必须先能读目录才能生成手册，而 bot 正是手册要建的东西之一。

第 0 批（手工）
平台管理员手工创建治理审计 bot（只读）。仅此一个，权限最低，不走流程。系统在它缺失时明确报错，不尝试自行创建。
第 1 批（走 G2）
其余 bot（架构开发只读、服务验证只读、运维发布 Writer）随变更请求包创建并授权，由平台管理员亲手执行。创建 bot 本就是平台级治理操作，天然属于 G2。
启动自检必须含负向探测：只验“令牌可用”不够——一个被误授写权限的只读 bot 不会有任何症状，权限边界却已失效。因此启动时须对每个 bot 做权限自检，其中只读 bot 的写操作探测必须被 OpenMetadata 拒绝；任一 bot 权限宽于职责，系统拒绝启动并指明是哪个 bot 多了哪一项。

推荐发布流程

代码版本
book-corpus-pipeline-v1.2.0
制品版本
book-corpus-pipeline:1.2.0
数据快照
version0612
查询副本
books-version0612-v1
线上指向
books-current

五类版本互相独立，不得用同一个标识兼表两类。“哪个版本在线”既不是分支状态也不是标签状态，而是线上指向的状态。

职责关系：GitHub 管理“管线如何实现”；Airflow 负责“实际执行”；OpenMetadata 管理“管线是什么、处理哪些资产、由谁负责以及运行了哪个版本”。

分支策略：主干开发 + 标签发布，不设 develop / release / prod 这类长期环境分支——环境差异不在代码里。开发与线上的区别只在于跑的是哪个数据快照、线上指向指向哪个查询副本。因此回滚是把指向指回去，既不回退代码也不重建数据。

阶段 4：上线与日常运维——运维发布 Agent 主责

调度器定死为 OpenMetadata 自带的 Airflow，不引入第二套独立部署的调度系统。运维发布 Agent 无 shell、够不着源码，只能部署制品引用所指向的作业定义。OpenMetadata 展示资产、血缘和运行结果，但登记的 Pipeline 实体是目录记录、不是执行主体——执行方始终是调度器。

1

检测数据变化

执行者
OpenMetadata 自带的 Airflow
动作
按日或按文件到达事件检查路径、大小、修改时间和校验和；无变化则结束。
权限
Raw 目录只读。
2

生成新版本

执行者
运维发布 Agent（Writer bot + Airflow 操作凭证）
动作
以新的 snapshot_version 执行 Profile、Curate 和版本索引构建，禁止覆盖旧 Parquet 与旧索引。
权限
文件写入、OpenSearch Builder、OM Writer。
3

质量门禁与发布

执行者
自动化检查；异常由运维负责人处理
动作
比较记录数、异常率、Schema、Gold Set 和查询结果，每项输出实际值与阈值的对比；全绿后，切换 Alias 作为一次独立的交互式审批送达运维负责人（G4），获批才切；失败则保持旧版本在线。
权限
Alias 修改仅授予发布步骤，不授予 Reader。
4

同步 OM 与告警

执行者
运维发布 Agent
动作
向 OM 更新数据版本、计数、质量、血缘和运行状态；连续失败、Schema 破坏性变化或权限错误时告警。
权限
OM Writer；只有平台对象或策略变更才升级 Admin。
调度形态：将现有 CLI 封装为 Airflow DAG：detect → profile → curate → index → validate → promote → metadata-sync。DAG 定义是代码，由架构开发 Agent 编写并走变更请求；DAG 运行是操作，由运维发布 Agent 触发。每步幂等、可重试，promote 前不影响线上；回滚只需将 books-current 指回上一版本，不回退代码、不重建数据。

凭证同源风险：调度器与治理目录属同一套部署，调度操作凭证极易串到平台管理权限上。二者必须严格分离，否则“任何 Agent 不持有平台管理凭证”会被从侧门绕过。

阶段 5：服务验证 Agent 的只读消费

只读消费的上线配置

  • 平台管理员：随 G2 变更请求包创建服务验证 bot（只读消费角色），不下发任何写权限。
  • 架构开发 Agent：发布 OpenMetadata MCP 与 Corpus Search MCP 的地址、工具清单、查询规则和 Agent 配置模板。
  • 服务验证 Agent：凭证经工具层注入（读不到明文），启动后完成双 MCP 连通性验证与越权负向验证。

实现载体:一切能力由 Agent 定义承载

本特性交付的是一个 Agent 定义包，不是一套应用程序。凡是这些机制表达不了的能力，只有三种下场：退化成提示词里的一句话（弱强制）、落到部署侧配置（不在包内）、或者根本没有载体。必须逐条认领载体。

需求分三层读,不可混为一谈

① Agent 长什么样
定义包本身的构造 · 载体：声明式配置 · 例：四个子 Agent、有无 shell、外部接入、凭证注入
② Agent 怎么工作
运行时行为与边界 · 载体：策略 + 工具 + skills + prompt · 例：闸门顺序、审批、工作区隔离、交接契约
③ 产出的管线长什么样
不由本包实现 · 是 Agent 运行时按 Spec 去写的东西 · 例：快照不覆盖、门禁项、回滚、幂等
第 ③ 层是 Agent 的验收标准，不是 Agent 的构建规格。把它当成“要在 Agent 定义里实现的功能”，是规划本特性最容易犯的错误——它们应当成为 Agent 的 prompt/skill 里给出的开发契约，以及每条管线 Spec 的验收用例。

强制力梯度,选错载体等于没做

策略 + 确定性工具
强 — 工具执行确定性代码；策略读工具的真实返回值并落状态，后续操作凭该状态放行
工具集裁剪
强 — 未授予的工具，模型根本调不到。最强也最省事的一道
策略（单用）
强 — 每次工具调用/结果无条件求值，模型没有选择权
Python 函数工具（单用）
中 — 一旦调用即执行确定性代码，但调不调用由模型决定
skill 捆绑脚本
弱 — 可列出、可读取，但没有“执行 skill 脚本”的工具；要跑得由 Agent 自己经 shell 调
skill 正文 / prompt
弱 — 模型主动加载才读到，读到也未必遵守；无强制加载机制

防谎报的闭环

策略有六个触发点，其中两个是关键：tool_call（派发前，可拒绝）与 tool_result（工具返回后、结果回给模型之前，能读到真实返回值）。由此可组出闭环：

①
Agent 调用确定性工具（如“只读核验”）
②
策略在 tool_result 上读工具的真实返回值，据此写会话标签
③
后续操作在 tool_call 上被策略检查该标签，不满足即拒绝
关键在于策略读的是工具的真实返回值，而不是模型的自述——所以模型声称“我已经核验过了”没有用。本特性中三处最该用这个组合：只读核验（证明治理变更真的执行到位）、bot 权限负向自检（证明只读 bot 真的写不了）、质量门禁判定（证明门禁真跑了且真通过）。

一个容易踩的坑

三个无 shell 的子 Agent 跑不了任何脚本。skill 的 scripts/ 目录对治理审计、运维发布、服务验证形同虚设——它们没有 shell，读到脚本也执行不了。这三个 Agent 需要的任何确定性逻辑，只能以 Python 函数工具提供。只有架构开发 Agent 有 shell，能跑捆绑脚本。

omnigent 的 Agent 定义机制全貌，另见 docs/omnigent-agent-definition.html。

身份与凭证:前置条件配置

对外只有两个前置依赖系统:OpenMetadata 与 GitHub。OpenMetadata 同时提供元数据管理与检索 MCP，调度器是它自带的 Airflow；四个子 Agent 全部访问它，只是权限不同。管线自己产出的检索服务与索引（本例中的语料检索 MCP、版本化查询副本）是交付物、不是前置依赖——启动 Agent 时它们尚不存在。

这些连接必须在启动 Agent 之前配好，否则失败会发生在流程中途而不是启动时。v1 以单一环境变量文件承载，由启动命令注入——运行时自身不解析该文件。图形化配置另立需求。

身份分两层,不可混用

人
使用 omnigent 自身的用户体系，与 OpenMetadata 相互独立。v1 不做统一登录。
Agent
使用 OpenMetadata bot 账号 + 各自的访问令牌。绝不继承登录用户的令牌。

Agent 不继承用户令牌的三个原因：其一，那会让平台管理员一使用系统，Agent 就自动获得管理员权限，G2 闸门当场失效；其二，四个子 Agent 需要不同权限，单一用户令牌拆不开；其三，阶段 4 按计划或事件触发，无人值守时根本没有登录用户，而会话令牌还会过期。

用 bot 的收益不只是“能用”，而是权限由 OpenMetadata 自己的角色与策略强制，不再依赖“我们没给它配写工具”这种自觉。

两种注入路径,按有无 shell 分

工具层注入
凭证配在工具定义上，调用时由运行时附加。无 shell 的 Agent 只能“使用”，读不到明文——治理审计、运维发布、服务验证属此类。
进程环境
Agent 有 shell 即可读取整个环境。仅适用于架构开发 Agent，且其环境中只放模型访问与代码托管两项。
这是本节的核心约束，而且比表面看起来更强：工具层注入的凭证值本身也来自进程环境（配置中以变量引用书写，解析时展开），因此对有 shell 的 Agent，工具层注入同样不构成隔离——它可以直接读那个环境变量。隔离真正成立的前提是 Agent 没有读取环境的手段。

这直接决定了给架构开发 Agent 哪种 bot：只能是只读 bot。它确实需要访问 OpenMetadata（查数据源定义、中间表与落地表的结构与归属），但给它写权限就等于把写凭证暴露给一个能读取整个环境的 Agent。生产环境的目录写入始终归无 shell 的运维发布 Agent。

代码托管:GitHub,不自建

omnigent 不提供 git 托管服务，本特性也不引入；v1 定死使用 GitHub。omnigent 已内置 git 认证接线——沙箱主机镜像内置凭证助手，从环境变量应答凭证请求，不落盘、对沙箱内任何用户生效、同时覆盖启动时克隆与 Agent 后续的拉取推送；未配置时公共仓库的匿名克隆不受影响。

给 Agent 的令牌不授予合并权限：这样“Agent 不合并变更请求”就从提示词层的约定变成凭证层的强制——托管服务直接拒绝，不依赖模型守规矩。

已知缺口:审计链在 v1 是断的

用户体系分离意味着同一个人在 omnigent、OpenMetadata、GitHub 里有三个身份；而 v1 又不读取目录的变更历史。两者叠加的后果是：系统无法证明“在 omnigent 里确认 G2 的人”就是“在 OpenMetadata 里执行手册的人”，也无法核实治理变更究竟由谁执行——核验只能证明“状态对了”，不能证明“是对的人做的”。

这是明知代价、主动接受的取舍（操作简单、团队规模小时可接受），不是疏漏。两条后续可选的补救，任选其一即可闭合：读取目录变更历史让核验报告自动记录实际执行人（成本最低，治理审计 bot 的只读权限已覆盖）；或统一登录，从根上让三个身份归一。在补上之前，“谁执行了治理变更”只能靠流程与人工记录约束。
