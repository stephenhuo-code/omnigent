omnigent Agent 定义与控制机制

一个 Agent 能被约束到什么程度，取决于你把行为放进了哪一层。本文说明 omnigent 的 Agent 定义结构、六种控制机制的强制力差异，以及“我要保证某个行为，该用哪一种”的选择规则。

规范以 docs/AGENT_YAML_SPEC.md 与运行时源码为准；本文是面向设计决策的导读。

一、Agent 定义包的结构

一个 Agent 是一个目录，不是一段代码。

my-agent/
├── config.yaml                 编排者本体
│                               spec_version / name / description
│                               executor      模型与 harness
│                               prompt        系统提示词
│                               os_env        本地文件与 shell 能力（不写=没有）
│                               terminals     长驻终端
│                               tools         子 Agent、函数工具、MCP
│                               guardrails    ask_timeout + policies
│                               spawn / async / cancellable / timers
│                               agent_session_sharing   会话共享授权
│                               params        供 skills 与 tools 读取的键值
├── agents/<name>/config.yaml    子 Agent，字段与上同（各自的 harness / 权限 / 策略）
├── tools/mcp/<name>.yaml        MCP 接入（自动发现，无需在 config.yaml 引用）
└── skills/<name>/
    ├── SKILL.md                 正文 + YAML frontmatter（name / description / user-invocable）
    ├── references/              资源：可被列出与读取
    ├── scripts/                 同上——注意：没有“执行 skill 脚本”的工具
    └── assets/
最重要的一条结构性事实：os_env 不声明，这个 Agent 就没有文件读写与 shell 工具。能力边界的第一道防线不是策略，是“压根不给”。

二、六种控制机制,强制力依次递减

选错载体等于没做。下表按强制力排序，不按使用频率。

机制强制力运行时行为
工具集裁剪
不给的就是没有		 强 未授予的工具，模型根本调不到。os_env 不写就没有 shell；MCP 的 tools: 白名单可只暴露部分工具。最强也最省事。
策略
guardrails.policies		 强 在六个触发点上无条件求值，返回 allow / deny / ask。模型没有选择权，也绕不过。
确定性工具 + 结果策略
组合用法		 强 工具执行写死的代码；策略在 tool_result 读真实返回值并落状态，后续操作凭状态放行。可防模型谎报。
Python 函数工具
type: function（单用）		 中 一旦被调用即执行确定性代码，消除“模型自己编结果”的风险；但调不调用由模型决定。
skill 捆绑脚本
skills/<n>/scripts/		 弱 可被列出（references/、scripts/、assets/）与读取（read_skill_file），但没有“执行 skill 脚本”的工具——要跑得由 Agent 自己经 shell 调，因此无 shell 的 Agent 根本用不了。
skill 正文 / prompt 弱 skill 需模型主动调用加载工具才读到，没有强制加载机制；读到也未必遵守。承载知识，不承载约束。
“确定性执行”≠“必然被执行”。函数工具保证“做的时候按代码做”，保证不了“一定会做”。只有策略是无条件求值的。

三、我要保证某个行为,该用哪一种?

    A -->|是| T1["不授予该工具
os_env 不声明 / MCP tools 白名单"]
    A -->|否| B{"是不是

走到最后一格就要警觉：凡是“必须发生”或“不得发生”的约束，落到 skill/prompt 就等于没落。此时应回头看能否改写成前几格之一。

四、策略:六个触发点与三种决策

sequenceDiagram
    autonumber
    actor U as 用户
    participant A as Agent 循环
    participant P as 策略引擎
    participant T as 工具

    U->>A: 新消息
    A->>P: request 阶段求值
    loop 每次 LLM 往返
        A->>P: llm_request 阶段求值
        A->>A: 调用模型
        A->>P: llm_response 阶段求值
    end
    A->>P: tool_call 阶段求值
    Note over P: allow 放行 / deny 拒绝 / ask 请人批准
    P->>T: 放行后派发
    T-->>P: 返回结果
    A->>P: tool_result 阶段求值
    Note over P: 可读真实返回值并写会话标签
    A->>P: response 阶段求值
    A-->>U: 最终回复
会话级

request / response

每轮各触发一次。用于整体准入、内容过滤、成本预算。

工具级

tool_call / tool_result

每次工具调用触发。前者在派发之前，可拒绝；后者在结果回给模型之前，能读真实返回值。

模型级

llm_request / llm_response

每次模型往返触发（一轮可能多次）。前者能看到完整提示词，后者是模型原始输出。

写法

guardrails:
  ask_timeout: 86400            # 审批等待上限（秒），可被单条策略覆盖
  policies:
    blast_radius:               # 短形式：可调用对象本身就是求值器
      type: function
      function: omnigent.policies.builtins.orchestration.blast_radius

    spawn_bounds:               # 工厂形式：arguments 是工厂 kwargs
      type: function
      function:
        path: omnigent.policies.builtins.orchestration.spawn_bounds
        arguments:
          max_dispatches_per_turn: 6
      on: [tool_call]           # 触发阶段；可窄化到单个工具：tool_call:sys_os_shell
      condition: {role: [admin, ops]}   # 标签门：仅当会话标签匹配时才生效
      ask_timeout: 3600         # 单条策略覆盖全局超时
策略有状态。它可读会话标签（事件里的只读快照），也可通过返回值写标签与状态；ASK 场景下仅在“批准”时才落状态，被拒或超时不留副作用。加上 condition 标签门，状态机可以半声明式地实现——这是把“流程顺序”变成硬约束的关键。

五、开箱可用的内置策略

先找现成的，找不到再自己写。以下按用途分组。

用途策略
编排与破坏半径blast_radius 按可逆性分级 shell 命令（强推/硬重置/根删除恒 DENY；推送/合并/部署 ASK 或 DENY；本地 git 放行）· spawn_bounds 每轮派发上限 · headless_subagent_purpose_guard 子 Agent 用途白名单 · worktree_guard 写入限制在工作区内 · read_only_os 拒绝一切改文件的调用
安全max_tool_calls_per_session · detect_loop · ask_on_os_tools · ask_on_add_policy · block_skills · enforce_sandbox · deny_pii_in_llm_request
成本与路由cost_budget · user_daily_cost_budget · subagent_cost_budget · deny_trivial_to_expensive_model · intent_based_authorization · risk_score_policy
外部系统github_policy · gdrive_policy / gmail_policy / gcalendar_policy
通用cel_policy 用 CEL 表达式声明式判定 · prompt_policy · working_dir 相关 · context 相关（任务切换、反复横跳检测）
cel_policy 值得特别注意：它把一条 CEL 表达式编译成策略，无需写 Python 就能表达大量条件判断，例如 event.type == "tool_call" && event.data.name == "sys_os_shell"。简单规则优先用它。

六、工具:三个层面的机制

“做成工具”不是单一手段，它同时提供三层约束，强度各异。

强

工具集即能力边界

未授予的工具，模型根本调不到。os_env 不声明就没有 shell；MCP 服务器可用 tools: 只暴露部分工具。

强

工具内部逻辑

callable: 指向的代码写死了“怎么做”，模型无从改变，也无法伪造返回值。

弱

是否调用

由模型决定。这一层的缺口必须用策略补——见下方闭环。

三种工具的声明

# ① Python 函数工具——确定性逻辑
tools:
  verify_state:
    type: function
    description: 只读核验实际状态是否满足断言。
    callable: my_pkg.tools.verify_state
    parameters:
      type: object
      properties: {assertions_path: {type: string}}
      required: [assertions_path]

# ② 子 Agent——独立 harness / 权限 / 策略
tools:
  reviewer:
    type: agent
    description: 独立评审改动。
    executor: {harness: claude-sdk, model: databricks-claude-sonnet-4-6}
    os_env: inherit
    pass_history: true

# ③ MCP——外部系统（放在 tools/mcp/<name>.yaml，自动发现）
name: catalog
transport: http
url: https://catalog.example.com/mcp
headers:
  Authorization: Bearer ${CATALOG_TOKEN}    # 解析期从进程环境展开
tools: [search, get_entity]                 # 白名单：只暴露这两个
凭证隔离有个前提。MCP 配置里的 ${VAR} 是从进程环境展开的。因此对有 shell 的 Agent，“工具层注入”并不构成隔离——它可以直接读那个环境变量。隔离真正成立的前提是该 Agent 没有读取环境的手段。给有 shell 的 Agent 配凭证时，一律按“它能看到明文”评估风险。

七、案例:把“必须做且做成”变成硬约束

目标：Agent 必须先完成核验、且核验确实通过，才允许进入下一阶段。只用工具会被跳过，只用 prompt 会被无视。

flowchart LR
    A["Agent 调用
verify_state 工具"] --> B["工具执行确定性代码
返回真实结果"]
    B --> C["策略在 tool_result 求值
读真实返回值"]
    C -->|通过| D["写会话标签
gate = verified"]
    C -->|未通过| E["不写标签"]
    D --> F["Agent 尝试进入下一阶段"]
    E --> F
    F --> G["策略在 tool_call 检查标签"]
    G -->|gate = verified| H["放行"]
    G -->|标签不符| I["拒绝
并说明缺什么"]

guardrails:
  policies:
    # ① 核验结果 → 写标签（只在工具真的返回通过时才写）
    record_verification:
      type: function
      function: my_pkg.policies.record_verification
      on: [tool_result:verify_state]

    # ② 下一阶段的操作 → 检查标签
    gate_next_phase:
      type: function
      function: my_pkg.policies.require_verified
      on: [tool_call:promote_release]
为什么这样才防得住谎报：策略读的是工具的真实返回值（tool_result 阶段），不是模型的自述。模型声称“我已经核验过了”不会写出标签，因此第 ② 条策略照样拒绝。

八、人机交互:ASK 如何送达到人

通道用途与性质
ASK → 收件箱策略返回 ask 时，运行时登记一条待处理请求并发出事件，跨会话聚合到收件箱页面。默认 url 模式会给出独立审批页链接。超时 / 拒绝 / 取消一律按未批准处理且不留副作用。
跨用户送达把会话共享给具名用户后，该会话会进入对方的列表，其待办随之出现在对方的收件箱。子 Agent 发起的请求会被镜像到父会话，因此同样可达。
审批权与访问权分开委派，默认关闭。sys_session_share 只能授访问级别，授不了审批权——Agent 不能自己给自己指定批准人。
任务回执子 Agent 完成时自动唤醒编排者（sys_read_inbox 取结果）。这是机器对机器的通道，不是人机通道，禁止轮询。
两个易混点。其一，sys_read_inbox（Agent 读子 Agent 回执）与 UI 的收件箱（人看待办）同名但不同物。其二，harness 自带的终端内审批提示与 omnigent 的策略 ASK 是两层——前者对无人值守的子 Agent 不可用（通常需绕过），后者始终有效。
会话共享的权限粒度是会话级，不是单条审批级。为让某人批一条审批，必须把整个会话共享给他，他会看到全部往来。设计时需要接受或规避这一点。

九、沙箱与凭证

os_env:
  type: caller_process
  cwd: .
  sandbox:
    type: linux_bwrap            # 省略则按平台默认（Linux/macOS 各一）
    write_paths: [.]
    allow_network: true
    egress_rules: ["* pypi.org/**"]
    credential_proxy:            # 明文根本不进沙箱，由 L7 出口代理挂上
      - type: databricks_cli
        profiles: [my-workspace]

不声明 os_env

该 Agent 没有文件与 shell 工具。这是最干净的隔离，也让“工具层注入的凭证读不到明文”真正成立。

声明了 os_env

Agent 继承整个进程环境。凭证隔离不成立，只能靠“环境里不放多余凭证”约束；要更强则用沙箱 + credential_proxy。

环境变量支持产品前缀别名（OMNIGENT_<NAME> 作为 <NAME> 的回退），可避免与宿主机同名变量冲突。运行时不解析 .env 文件——须由启动命令注入，例如 uv run --env-file .env。

十、速查:常见约束该放在哪

你想保证的放在哪强度
这个 Agent 不能碰文件 / 跑命令不声明 os_env强
只暴露外部系统的部分能力MCP 的 tools: 白名单强
不许强推 / 硬重置 / 根删除blast_radius（恒 DENY，无审批放行）强
推送 / 部署要人批准blast_radius 的 ASK 档强
写入不许越出工作区worktree_guard强
这个 Agent 只读，不许改文件read_only_os + 不授予写工具强
每轮派发的子 Agent 不超过 N 个spawn_bounds强
流程必须按顺序推进,不许跨越策略状态机（tool_result 写标签 + tool_call 检查 + condition 标签门）强
某步骤必须做且必须做成确定性工具 + tool_result 策略 + tool_call 门控强
启动前必须校验前置条件自写策略在首个工具调用上拦截——运行时没有 Agent 启动自检钩子强
某个计算要按确定逻辑做Python 函数工具中
某类任务的做法与套路skill 正文弱
整体角色设定与行为基调prompt弱
三条最容易踩的坑。其一，skill 没有强制加载机制，把约束写进 skill 等于写进提示词。其二，无 shell 的 Agent 跑不了 skill 的 scripts/，它们的确定性逻辑只能做成函数工具。其三，运行时没有启动自检钩子，“首轮预检”这类做法是写在提示词里靠模型自觉的，要硬约束必须自写策略。
